# Rusty Modbus — Release Readiness Audit

**Date:** 2026-06-01 · **Target:** open-source v0.1.0 on crates.io · **Method:** spec-grounded multi-agent audit (65 agents) cross-checked by hand.

## Executive summary

The **protocol core is genuinely excellent** and largely spec-compliant: the sans-IO codec, MBAP framing, CRC-16, the TLS 1.3 mutual-auth handshake, the transaction ring, and the end-to-end zero-copy read path all hold up against Modbus Application Protocol V1.1b3, the Modbus/TCP Implementation Guide, the Modbus over Serial Line spec, and the Modbus/TCP Security spec. `#![forbid(unsafe_code)]` is enforced everywhere and the foundation crates are genuinely `no_std`.

What blocks release is **not** the codec — it is the transports, the integration wiring (pool/gateway/TLS-role features that are implemented but never connected), real-device RTU behaviour, a handful of network-reachable robustness bugs, and crates.io packaging. None of the blockers are deep architectural problems; most are small, surgical fixes.

Sources audited: MODBUS Application Protocol V1.1b3 (§4.1 PDU/253-byte cap, §4.2 big-endian, §4.5 + §6 per-FC validation-order state diagrams, §7 exception codes), MODBUS Messaging on TCP/IP Implementation Guide V1.0b (MBAP, §4.2 connection management), MODBUS over Serial Line V1.02 (RTU framing, CRC-16/0xA001, t3.5/t1.5 timing, address rules), and the MODBUS/TCP Security spec (TLS, mutual auth, role OID).

**Verdict:** strong foundation, ~2–3 focused PRs of correctness + packaging work away from a credible v0.1.0.

## 🔴 Critical blockers

### (rtu-framing) Pipelined ModbusClient over an RTU transport silently breaks every transaction (txn-id / slot-0 mismatch)
- **Evidence:** ModbusClient is generic over any TransportSink (crates/rusty-modbus-client/src/client.rs:22, 56) and from_transport is public (client.rs:64). RTU transport halves SerialSink/RtuTcpSink impl TransportSink/TransportStream and are publicly re-exported (crates/rusty-modbus-rtu/src/lib.rs:18-20; serial.rs:107, rtu_tcp.rs:88), so `ModbusClient::from_transport(serial_sink, serial_stream, cfg)` compiles and is an obvious usage. But send_request always builds an MBAP frame with an allocated transaction id (client.rs:154-165) registered in ring slot `id % 16` with id starting at 1 (crates/rusty-modbus-client/src/transaction.rs:42, 68-90). The RTU encoder maps FrameHeader::Mbap(h) -> uses only h.unit_id, dropping the txn id (crates/rusty-modbus-frame/src/rtu.rs:63-66; rtu_tcp.rs:74-77). On the response path the reader maps EVERY RTU frame to TransactionId(0) (crates/rusty-modbus-client/src/reader.rs:38-42) and complete() requires the stored slot's txn_id to equal the lookup id (transaction.rs:104-114). Since pending ids are 1,2,...,65535,0 the response→TransactionId(0)/slot 0 only matches the single request whose id happens to be exactly 0; the other 65535 requests get their response dropped and fail via the 500ms sweep timeout (client.rs:85-90, transaction.rs:130-146). This path is fully reachable, has zero test coverage (all RTU tests in crates/rusty-modbus-rtu/tests/rtu_over_tcp.rs and the conformance tests drive the transport halves directly, never through ModbusClient), and is undocumented. The gateway, by contrast, correctly drives RTU halves one-at-a-time (crates/rusty-modbus-gateway/src/gateway.rs:202-213), which is why it works.
- **Fix:** Either provide a dedicated single-in-flight RTU client (recommended — RTU is half-duplex, one transaction at a time per RTU-MASTER-001) or, at minimum, make the generic client safe over RTU: detect the RTU transport and force max_in_flight=1 plus map the sole pending transaction regardless of id. Concretely, the reader should not blindly use TransactionId(0); for RTU it should complete whatever single transaction is outstanding. Until fixed, change from_transport / RTU sink visibility or add a prominent doc warning that ModbusClient must not be used over RTU sinks, and add a regression test that send_request over an RtuOverTcpCodec server returns the response instead of timing out.

### (client-concurrency) Background reader treats idle read-timeout as fatal: client dies after read_timeout of inactivity
- **Evidence:** reader.rs:33 the reader loops on stream.recv(). For TCP, TcpRecvStream::recv() wraps the read in timeout(read_timeout, ...) and returns Err(TransportError::Timeout) on an idle gap (crates/rusty-modbus-tcp/src/connect.rs:115-118). ModbusClient::connect() sets read_timeout: Some(config.timeout) (client.rs:44-46, default 5s); from_transport() inherits whatever the caller configured (TcpConfig default read_timeout = 30s, crates/rusty-modbus-tcp/src/config.rs:29; serial/rtu_tcp behave identically, crates/rusty-modbus-rtu/src/serial.rs:130-135, rtu_tcp.rs:111-117). The reader's catch-all arm reader.rs:61-73 does NOT distinguish TransportError::Timeout from a real I/O failure: it does connected.store(false), txn_mgr.cancel_all(...ConnectionAborted...), and break — permanently terminating the reader task. After this, is_connected() is false so every subsequent request returns ClientError::NotConnected (client.rs:142-143), and any in-flight request at that moment is failed with a fabricated ConnectionAborted error. A client that connects then idles longer than read_timeout (e.g. any poller slower than 5s/30s) is silently and permanently broken. No test covers idle-reader survival, so the 538-test baseline does not catch it.
- **Fix:** In reader.rs, match TransportError::Timeout explicitly and `continue` the loop (an idle read timeout is normal and benign; per-request timeouts are already handled by sweep_timeouts). Only Disconnected and genuine I/O/Frame errors should tear the reader down. Alternatively, give the reader its own stream with read_timeout = None and rely solely on the sweep + TCP keepalive for liveness. Add a regression test: connect, sleep > read_timeout, then issue a successful request.

### (gateway) Response unit_id is forged from the request, not validated against the RTU response
- **Evidence:** gateway.rs:222-223 calls translator::rtu_to_mbap(&rtu_response, txn_id, unit_id) passing the request's unit_id; translator.rs:23-33 builds the MBAP header from that passed-in unit_id and completely ignores rtu_response.unit_id() / FrameHeader::Rtu{unit_id} decoded from the wire (rtu_tcp.rs:47-54). On a shared RTU bus a stale or cross-talk frame from a different slave (different unit_id) would be relayed to the TCP client stamped with the requested unit_id, masking the mismatch. Likewise the response function code is not checked against the request FC. The client cannot detect the substitution because it trusts the gateway-stamped unit_id.
- **Fix:** Compare rtu_response.unit_id() against the requested unit_id (and ideally response FC vs request FC modulo the 0x80 exception bit). On mismatch, discard the frame and return GatewayTargetDeviceFailedToRespond (0x0B) rather than relaying a misrouted response.

### (packaging-release) Inter-crate dependencies have no version field — cargo publish will fail for every dependent crate
- **Evidence:** Every inter-crate dep across all publishable crates is path-only with no version, e.g. crates/rusty-modbus-frame/Cargo.toml:15-16 (rusty-modbus-types/codec), crates/rusty-modbus-client/Cargo.toml:15-18, crates/rusty-modbus/Cargo.toml:15-24, crates/rusty-modbus-tls/Cargo.toml:15-18, etc. crates.io strips `path` on publish and rejects any dependency on a published crate that lacks a `version`, with: 'all dependencies must have a version specified when publishing'. The CI `cargo publish --no-verify` flag (.github/workflows/ci.yml:113 onward) only skips the compile-verification pass; it does NOT skip manifest/dependency validation, so the publish of rusty-modbus-codec (first crate that depends on another, line 119) will hard-fail. types publishes fine (no deps), then codec fails immediately, leaving a half-published registry state.
- **Fix:** Add a version requirement to every inter-crate dependency alongside the path, e.g. `rusty-modbus-types = { path = "../rusty-modbus-types", version = "0.1.0" }`. Best practice with the shared workspace version: add `version.workspace = true` is not valid on deps, so either (a) hardcode `version = "0.1.0"` on each, or (b) define each crate in `[workspace.dependencies]` once with both path and version and use `rusty-modbus-types.workspace = true` in members. Option (b) keeps versions in one place and is the recommended pattern for a lockstep workspace. Run `cargo publish -p rusty-modbus-codec --dry-run` after the fix to confirm validation passes before tagging.

## HIGH (confirmed) — evidence + fix

### (codec-fc) 253-byte MAX_PDU ceiling is never enforced on encode or decode (PDU-02)
- **Evidence:** grep for MAX_PDU_SIZE/253/MAX_PDU across crates/rusty-modbus-codec/src returns ZERO hits — the constant MAX_PDU_SIZE=253 (crates/rusty-modbus-types/src/constants.rs:7) is never used by the codec. Confirmed empirically: ReadCoilsResponse{byte_count:255,...}.encode_into → 257-byte PDU (crates/rusty-modbus-codec/src/response/bit_read.rs:60-77, encoded_len = 2 + byte_count); ReadHoldingRegistersResponse byte_count=255 → 257 bytes (response/reg_read.rs:76-93); WriteFileRecordRequest with byte_count=255 decodes OK → 257-byte PDU (request/file.rs:135-156); a Custom-FC request with 300 bytes of data decodes OK (decode.rs:103). PDU-02 (critical) requires the codec to enforce the 253-byte ceiling regardless of transport, and that read/write quantity limits keep the PDU <= 253. Per-FC quantity caps incidentally bound the *named* read/write FCs to <=252, but file-record (FC14/15), FIFO, MEI, diagnostics, and Custom FCs are unbounded because their length is driven by a u8/u16 byte_count or a raw slice with no 253 check.
- **Fix:** Add a MAX_PDU_SIZE (253) check at the top-level decode_request/decode_response dispatchers (reject any PDU slice longer than 253) and in every Encode::encode_into (return EncodeError if encoded_len() > 253, or add an EncodeError::PduTooLarge variant). Most surgical: validate `pdu.len() <= MAX_PDU_SIZE` in decode_pdu_ref/decode_request/decode_response, and `len <= MAX_PDU_SIZE` after computing encoded_len() in each encode_into.

### (rtu-framing) RTU inter-frame (t3.5) delay is computed but never enforced on the wire
- **Evidence:** RtuConfig::interframe_delay() correctly computes 3.5 char-times (<=19200 baud) and the fixed 1750us (>19200) (crates/rusty-modbus-rtu/src/config.rs:84-92), but a workspace grep shows it is referenced ONLY by its own unit tests (config.rs:112,124,135) and the rtu_over_tcp integration test — never in serial.rs or rtu_tcp.rs send/recv paths (`grep interframe_delay` over src excluding tests returns nothing). SerialTransport::open only forwards baud/data/parity/stop to tokio-serial and wraps it in Framed<RtuCodec> (crates/rusty-modbus-rtu/src/serial.rs:38-60); there is no t3.5 gap before transmit and no silence-based end-of-frame detection. The RtuCodec itself documents 'frame boundaries ... handled by the transport layer' (crates/rusty-modbus-frame/src/rtu.rs:2-5,19) but no transport layer actually implements it.
- **Fix:** Apply interframe_delay() as a guard time before each serial transmit (and ideally as the read end-of-frame timeout). Document explicitly that RTU framing on serial is delegated to OS/driver buffering if that is the intended posture, but note the t3.5 transmit gap is a normative MUST (RTU-TIMING-001) and is currently absent.

### (rtu-framing) RTU inter-character (t1.5, 750us above 19200 baud) timeout is not implemented at all
- **Evidence:** The spec (RTU-TIMING-002/003) requires aborting an in-progress frame after >1.5 char-times of silence, with a fixed 750us value above 19200 baud. There is no t1.5 constant or logic anywhere: grepping crates/rusty-modbus-rtu and crates/rusty-modbus-frame for 750 / inter-char / t1.5 / char_timeout yields only the unrelated 1750us FIXED_INTERFRAME_DELAY (crates/rusty-modbus-rtu/src/config.rs:73). serial.rs has no inter-character timer; the RtuCodec.decode validates CRC over the whole buffer (crates/rusty-modbus-frame/src/rtu.rs:37-47) and relies on the transport to deliver a complete frame, so a gapped frame is not actively detected/discarded — it would simply fail CRC if buffered together or hang/partial-decode depending on driver delivery.
- **Fix:** Add a FIXED_INTERCHARACTER_TIMEOUT (750us) and a calculated 1.5-char value, and enforce it in the serial read path to discard incomplete frames (RTU-TIMING-002). If full enforcement is out of scope for a tokio-serial-based implementation, document this as a known deviation explicitly rather than implying framing is handled.

### (server-validation) spec_validation.rs tests the unused validator, not the server (false confidence)
- **Evidence:** spec_validation.rs:8 imports codec validate; ordering tests (lines 17,118-122) call validate.rs directly, never the live server. No live test covers bad-qty+bad-addr or FC05 bad-value+bad-addr.
- **Fix:** Add handler process_request tests: FC01 qty=5000+addr=0xFFFF -> 0x03; FC05 value=0x1234+bad addr -> 0x03; FC10 valid qty+overflow -> 0x02.

### (tls-security) Role extraction and authorization layer are dead code — never wired into any server
- **Evidence:** role.rs:19 `extract_role` is public but the only callers are lib.rs re-export and the conformance test (spec_tls_transport.rs:32-35). config.rs:56-110 define `authz_callback`, `AuthzRequest`, `AuthzDecision` but a workspace grep shows zero invocations outside config.rs/lib.rs/tests. The TLS crate has NO server-side request processing: grep for DataStore/handle_request/process_request in crates/rusty-modbus-tls/src returns nothing; TlsServerListener::accept (listener.rs:38-56) only returns raw split sink/stream halves and never inspects peer certificates. No crate (server/gateway/cli) depends on rusty-modbus-tls except conformance/facade/python/benchmarks, and none extract a role, build an AuthzRequest, or call the callback. Consequently Modbus Security R-04/R-16/R-17/R-23/R-30/R-31 (role-based AuthZ, NULL-role default to AuthZ, exception 0x01 on denial) are entirely unimplemented even though the public API implies they exist.
- **Fix:** Either (a) implement the wiring: after handshake, read TlsStream::get_ref().1.peer_certificates(), call extract_role on the leaf cert, store the role on the connection, and invoke authz_callback per request returning ExceptionCode::IllegalFunction (0x01) on NotAuthorized; or (b) if out of scope for this release, remove/feature-gate the authz_callback/AuthzRequest/AuthzDecision/extract_role public API and document clearly in the crate docs that only TLS transport (not Modbus role authorization) is provided. Shipping a public 'authorization' API that is silently a no-op is a security-misleading footgun.

### (tls-security) Client only supports IP-address ServerName — no hostname/SNI verification
- **Evidence:** connect.rs:32-50: TlsTransport::connect takes a SocketAddr and hard-codes `ServerName::IpAddress(addr.ip().into())` (connect.rs:46). There is no way to supply a DNS hostname, so SNI is never sent and the server cert is validated against the IP only. The integration test (tls_transport.rs:32-37) works only because the test server cert includes an IP SAN for 127.0.0.1. Real CA-signed server certs (R-45 recommends CA-signed) typically carry DNS SANs, not IP SANs, so production deployments addressing servers by hostname cannot verify the certificate.
- **Fix:** Add an optional server-name/SNI field to TlsClientConfig (ServerName::try_from(&str)) and fall back to IP only when absent. This is needed for interoperability with normally-issued CA certificates and for correct hostname verification.

### (tls-security) rustls-webpki 0.103.10 vulnerable (RUSTSEC-2026-0104 / GHSA-965h-392x-2mh5, GHSA-xgp8-3hg3-c2mh)
- **Evidence:** Cargo.lock pins rustls-webpki 0.103.10 (rustls 0.23.37). cargo deny check advisories reports RUSTSEC-2026-0104 with fix in >=0.103.12. This is the certificate-path-validation library used by both client and server verifiers in tls_config.rs, so the panic is directly reachable by the TLS code under audit. (Baseline notes this exists; flagging because it lives squarely in the TLS attack surface.)
- **Fix:** Run `cargo update -p rustls-webpki` to pull >=0.103.12 and re-run cargo deny + the TLS conformance/integration tests. This is a one-line lockfile bump and should land before the public release.

### (server-conn) Connection counter leaks if set_nodelay fails after increment
- **Evidence:** crates/rusty-modbus-tcp/src/listener.rs:84-87. The active-connection counter is incremented with `self.active_connections.fetch_add(1, Ordering::Relaxed)` at line 84, and the very next line `stream.set_nodelay(self.config.tcp.tcp_nodelay)?;` (line 87) uses `?` to return early on error. The ConnectionGuard (which decrements on Drop) is not constructed until line 95, AFTER the fallible `set_nodelay` call. So if set_nodelay returns Err (rare but possible: socket already closed/reset by peer mid-accept, ENOBUFS), accept() returns Err with the counter permanently incremented and no guard ever created. Repeated occurrences monotonically inflate the counter until it reaches max_connections, at which point the server silently refuses ALL further connections (listener.rs:81-82 `if current >= self.config.max_connections { continue; }`) — a permanent denial-of-service with no recovery path.
- **Fix:** Construct the ConnectionGuard immediately after the fetch_add (before set_nodelay), so any subsequent `?` early-return drops the guard and decrements. Alternatively perform set_nodelay before the increment. Either way, ensure no fallible operation sits between the increment and guard construction.

### (server-conn) Tight CPU busy-loop on persistent accept() errors (fd exhaustion turns into 100% CPU spin)
- **Evidence:** crates/rusty-modbus-server/src/server.rs:126-137 (and identically in crates/rusty-modbus-gateway/src/gateway.rs:100-109). The accept_loop does `result = listener.accept() => { if let Ok((sink, stream, _addr, guard)) = result { ... } }` with the comment `// Accept error — could be transient; continue.` On an Err result there is no backoff/sleep — the select immediately re-polls listener.accept(). TcpServerListener::accept (listener.rs:70 `self.listener.accept().await?`) propagates IO errors out rather than retrying internally. For a persistent error such as EMFILE/ENFILE (file-descriptor exhaustion) — which is exactly what happens under a connection-flood DoS — accept() fails immediately and repeatedly, producing an unthrottled hot loop that pins a core at 100% and starves the rest of the runtime. This converts a recoverable resource-exhaustion condition into a self-amplifying outage.
- **Fix:** On accept() Err, distinguish per-connection/transient errors (continue) from fatal ones, and at minimum insert a short backoff sleep (e.g. tokio::time::sleep(Duration::from_millis(10..100))) before retrying, matching the standard hyper/tokio accept-loop pattern. Optionally log the error so operators can see fd exhaustion.

### (server-conn) Graceful shutdown does not wait for or close in-flight connections (documented behavior unimplemented)
- **Evidence:** crates/rusty-modbus-server/src/server.rs:80-85. The doc comment on stop() reads `/// Graceful shutdown: stop accepting, wait for in-flight, close connections.` but the body only does `let _ = self.shutdown_tx.send(true);` then `tokio::time::sleep(Duration::from_millis(100)).await;`. The shutdown signal is delivered ONLY to accept_loop (which stops accepting new connections, server.rs:138-142). The per-connection tasks spawned at server.rs:131-134 are given conn_store/conn_device_id/unit_id but NOT a shutdown receiver, so they keep running until the remote peer disconnects (or the 30s read timeout fires). stop() therefore neither waits for in-flight requests to complete nor closes existing connections; it just stops accepting and returns after a fixed 100ms. On Drop (server.rs:100-106) only accept_handle.abort() is called — the spawned connection tasks are detached and orphaned, continuing to run (and hold sockets/store references) until the Tokio runtime itself is dropped.
- **Fix:** Either implement real graceful shutdown — broadcast shutdown to each connection task (give handle_connection a watch::Receiver and select! it against stream.recv()), track spawned tasks with a tokio JoinSet or tokio_util TaskTracker, and await them up to shutdown_timeout before forcibly aborting — or downgrade the doc comment to accurately describe the current best-effort behavior. The current comment is misleading for a public release.

### (pool) PriorityDevice.max_connections is dead config — per-device connection caps are never enforced
- **Evidence:** crates/rusty-modbus-pool/src/config.rs:43-48 defines PriorityDevice { addr, max_connections }, but grep shows the only reads of any max_connections in the pool crate are config.max_connections at pool.rs:55 and pool.rs:120. PriorityDevice.max_connections (pd.max_connections) is never read anywhere (confirmed: `grep -rn '\.max_connections|pd\.max' crates/rusty-modbus-pool/src` returns only the global field). get() at pool.rs:103-149 enforces only the global config.max_connections cap; it never counts how many connections already exist to a given priority addr. A caller can open far more than the configured per-device limit to a single priority device, defeating the stated two-pool §4.2.1 semantics and potentially overwhelming a device that advertised a low max_connections.
- **Fix:** Either enforce pd.max_connections in get() (count idle+active entries with entry.addr == addr and reject/evict when the per-device cap is reached) or remove the field and document that only a global cap is enforced. For a public release, silently ignoring a documented config field is a trap; pick one and make it match the doc comment.

### (pool) Priority idle connections count toward max_connections but are never evictable — non-priority starvation / permanent Exhausted
- **Evidence:** pool.rs:119 computes total = active_count + idle.len() (priority + non-priority idle both counted). pool.rs:120-127: if total >= max_connections it calls find_evictable(), which (pool.rs:216-227) only ever returns indices of NON-priority idle entries. If the pool is full of priority idle connections (e.g. pre_connect populated them, or many priority devices), find_evictable returns None and get() returns PoolError::Exhausted (pool.rs:126) for any new non-priority address — even though those priority connections are idle and the pool is doing no work. There is no upper bound separating the two sub-pools, so priority connections can monopolize the entire global budget and permanently lock out non-priority traffic. This contradicts the 'two-pool' intent where the pools should be sized independently.
- **Fix:** Track separate budgets for priority vs non-priority (e.g. priority capacity reserved, non-priority gets max_connections - priority_in_use), or at minimum allow new connections to proceed when the only thing blocking them is idle priority connections that are not to the requested addr. Add a test that fills the pool with priority idle entries and asserts a non-priority get() still succeeds.

### (pool) Backoff implemented and tested but never wired into the pool — reconnects have no backoff
- **Evidence:** crates/rusty-modbus-pool/src/backoff.rs fully implements Backoff with next_delay()/reset() and unit tests (lines 41-80), and PoolConfig carries a backoff: BackoffConfig field (config.rs:21-22). But grep for `Backoff`/`backoff` across pool.rs, connection.rs, health.rs, lib.rs shows the type is only re-declared as a module (lib.rs:9); it is never constructed or invoked in get(), spawn_pre_connect(), or the health task. Pre-connect failures (pool.rs:189-204) just exit the spawned task with no retry at all, and get() failures bubble up immediately. The advertised reconnect-with-exponential-backoff behavior does not exist on any live code path, so a flapping device produces unthrottled reconnect attempts (or, for pre-connect, never reconnects).
- **Fix:** Either integrate Backoff into a real reconnect loop (pre-connect retry task and/or get() retry path using config.backoff) or remove the unused machinery and the backoff config field before release to avoid implying behavior that isn't there. If kept, add an integration test that observes increasing delays under repeated failure.

### (gateway) RTU half-duplex bus is not serialized — concurrent requests race on the same backend
- **Evidence:** gateway.rs:104 spawns one task per accepted TCP connection (handle_tcp_connection), and gateway.rs:166-203 (forward_to_backend) opens an independent RtuOverTcpTransport::connect to the backend for each request with no shared lock/mutex/semaphore keyed on backend_addr. A real RTU serial line (the documented production target per config.rs:38-45) is half-duplex: only one request/response transaction may be on the wire at a time. With multiple TCP clients (max_tcp_connections default 64) all mapped to the same backend, or even a single pipelined client, multiple transactions hit the same physical bus simultaneously. On a real serial port this corrupts framing; on the RTU-over-TCP test backend each gets its own socket so the bug is hidden by the test harness (gateway_tests.rs spawns a new device task per accept). There is no per-backend transaction queue/serialization anywhere in the crate.
- **Fix:** Introduce a per-backend async mutex (e.g. HashMap<SocketAddr, Arc<tokio::sync::Mutex<BackendConn>>>) so that all requests routed to a given backend are serialized into a single in-flight transaction at a time, matching RTU half-duplex semantics. This also naturally enables connection reuse (see next finding).

### (gateway) New backend TCP connection opened and torn down on every single request
- **Evidence:** gateway.rs:173-203: for every TCP request, forward_to_backend calls RtuOverTcpTransport::connect(backend_addr, ...) (rtu_tcp.rs:38-62 does a fresh TcpStream::connect each time), sends one frame, awaits one response, then drops both halves at function end. There is no connection pool or cached backend handle. The gateway crate has no dependency on rusty-modbus-pool. This means connection-establishment latency (TCP handshake) is paid per request, and for a real serial backend it implies re-opening the port per request. Under load this exhausts ephemeral ports / file descriptors and adds large latency. The cost is masked in tests because the local RTU-over-TCP device accepts unlimited connections.
- **Fix:** Cache and reuse one backend connection per backend_addr (guarded by the per-backend mutex from the previous finding), reconnecting only on error. For real serial deployment, hold a single persistent serial handle per port.

### (panic-dos-sweep) Network-reachable client panic: Read Coils / Read Discrete Inputs index by requested quantity, not returned byte_count
- **Evidence:** crates/rusty-modbus-client/src/methods/coils.rs:49-52 (read_coils) and :95-98 (read_discrete_inputs) loop `for i in 0..quantity as usize { coils.push(rc.coil(i)); }` over the quantity the CLIENT requested. `rc.coil(i)` (crates/rusty-modbus-frame/src/owned.rs:68-72 OwnedReadCoilsResponse::coil, and 119-123 for discrete inputs) does `self.coil_status[index / 8]` with no bounds check (it is documented `# Panics`). The decoder OwnedReadCoilsResponse::from_pdu (owned.rs:39-60) only validates that coil_status.len() == byte_count (internal consistency); it does NOT verify byte_count >= ceil(requested_quantity/8). A malicious or malfunctioning server replying to a Read-Coils request for e.g. 100 coils with a well-formed PDU carrying byte_count=1 (one data byte) passes decode, then rc.coil(99) indexes coil_status[12] on a 1-byte slice -> index-out-of-bounds panic. This runs in the caller's task on a response decoded from raw network bytes in reader.rs, so a remote peer can crash the client (DoS). The analogous register read paths are NOT affected because they use the safe chunks_exact(2) iterator .registers() (registers.rs:49,129,319) rather than the index-based .register(i).
- **Fix:** Do not drive the loop by the requested quantity. Either (a) clamp the loop to the actually-returned bits: iterate `for i in 0..(rc.byte_count as usize * 8).min(quantity as usize)` and/or return ClientError::Codec(ByteCountMismatch) when `rc.byte_count < (quantity as usize).div_ceil(8)`; or (b) change coil()/the loop to use a checked accessor (return Option / use get()). Add a regression test feeding a short coil response for a large requested quantity and asserting an Err, not a panic.

### (panic-dos-sweep) Unbounded client loop in Read Device Identification controlled by server more_follows flag (livelock DoS)
- **Evidence:** crates/rusty-modbus-client/src/methods/device_id.rs:30-85. The `loop` re-issues a request whenever the server sets `dev_id.more_follows` (line 81) and continues with `next_object_id = dev_id.next_object_id` (line 84). There is no iteration cap and no check that next_object_id strictly advances. A malicious server can set more_follows=true on every reply (optionally pinning next_object_id), making the client spin in an unbounded request/response loop forever. Memory does not grow unbounded, but the call never returns — a remotely triggerable livelock. Each round-trip is rate-limited by the server, so it is not a busy-spin, but the operation has no termination guarantee.
- **Fix:** Cap the number of continuation iterations (e.g. <= 256, the object-id space) and/or require next_object_id to increase monotonically; otherwise break with a Codec error. This bounds the conversation regardless of server behavior.

### (performance) Sink Mutex held across socket flush serializes all request submission, partially defeating pipelining
- **Evidence:** crates/rusty-modbus-client/src/client.rs:170-179: `let mut sink = self.sink.lock().await; if let Err(e) = sink.send(frame).await {...}`. `TcpSink::send` (crates/rusty-modbus-tcp/src/connect.rs:83-93) calls `futures_util::SinkExt::send`, which performs poll_ready + start_send + poll_flush — i.e. it drives the actual socket write to completion while the async mutex is held. The semaphore allows up to 16 in-flight (client.rs:70-71, 147-151) and the background reader (reader.rs) demuxes responses concurrently, so READS overlap; but request SUBMISSION is fully serialized: task B cannot encode/queue its frame until task A's flush completes and releases the lock. The pipeline's write side therefore cannot overlap or batch. Under a slow/backpressured socket (poll_flush returns Pending), the mutex is held across the await point, blocking every other sender on that connection for the duration. This is the canonical 'single lock on the send path defeats pipelining' pattern called out in the review brief.
- **Fix:** Use `SinkExt::feed` (start_send without flush) under the lock and move the flush outside the critical section, or drain a per-connection MPSC channel of frames in a dedicated writer task (writer owns the sink, no shared mutex). At minimum, ensure the lock is not held across `poll_flush` when the socket is backpressured. Document the current serialization so users understand single-connection write throughput limits.

## MEDIUM (confirmed) — evidence + fix

### (codec-fc) Function code 0x00 accepted as Custom(0) instead of rejected (PDU-01)
- **Evidence:** decode_request(&[0x00, 0x11, 0x22]) returns Ok(RequestPdu::Custom(0, [17,34])). In crates/rusty-modbus-types/src/function.rs:113-136 from_byte maps byte 0x00 → Custom(0x00), and decode.rs:103 routes Custom(fc) to RequestPdu::Custom without rejecting fc==0. PDU-01 (high) states the function code is one byte in 1..255; 0 is invalid. FunctionCode::from_raw(0x00) also returns Some(Custom(0)) and there is an explicit test asserting this (function.rs:264-268).
- **Fix:** Reject function code 0x00 at decode_request (and ideally make FunctionCode::from_raw(0) return None or a dedicated Invalid variant). At minimum, in decode_request add a guard returning DecodeError::UnknownFunctionCode(0) for fc==0 before dispatch.

### (codec-fc) FC14/FC15 file-record decode omits byte-count range and per-sub-request reference-type validation
- **Evidence:** ReadFileRecordRequest::decode (crates/rusty-modbus-codec/src/request/file.rs:72-92) and WriteFileRecordRequest::decode (file.rs:135-156) only check byte_count == remaining length; they store sub_requests as a raw &[u8] and never call FileSubRequest::decode, so the spec-mandated Reference Type == 6 check (file.rs:37-40) is never applied during dispatch. The byte-count ranges are also unchecked: FC14 requires 0x07<=ByteCount<=0xF5 and FC15 requires 0x09<=RequestDataLength<=0xFB (FC14/FC15 reqs, Figures 24/25 → exc 03). Confirmed: decode_request(&[0x14,0x00]) → Ok(byte_count:0, sub_requests:[]) and decode_request(&[0x14,0x03,0x06,0x00,0x01]) → Ok despite byte_count 3 being below the 0x07 minimum.
- **Fix:** In FC14/FC15 decode, validate byte_count is within the spec range (0x07..=0xF5 read, 0x09..=0xFB write) and iterate FileSubRequest::decode over the sub-request region so reference-type==6 and record-number<=0x270F are enforced (or document explicitly that sub-request validation is delegated to the server layer and add a note that ref-type is not checked in the codec).

### (mbap-tcp) Client does not verify response function code against request at the transaction layer (RESP-FC-01)
- **Evidence:** The reader matches a response to a request purely by MBAP transaction ID (reader.rs:36-47) and the TransactionManager stores the request FunctionCode but never compares it to the decoded response (transaction.rs:99-115 complete() ignores function_code). Per TCP Guide §4.4.1.3 (RESP-FC-01), the client MUST verify the response FC matches the request FC (or is request_FC|0x80) and otherwise signal a Negative Confirmation. Here, if a (compromised or buggy) server returns the correct txn id but a *different* valid FC, the response is decoded as whatever that FC dictates and delivered to the caller. The per-method match arms catch the mismatch indirectly (e.g. registers.rs:48-54 the catch-all returns ClientError::Codec(UnknownFunctionCode(0))), so it does fail closed — but as a misleading 'UnknownFunctionCode(0)' rather than a proper negative-confirmation/FC-mismatch error, and only because each typed method happens to match exactly one variant. A raw/custom-FC path or any future method that accepts multiple variants would not be protected. There is no test exercising txn-id-correct-but-FC-wrong.
- **Fix:** Add an explicit FC check in the transaction/reader layer: store the request FC (already in PendingTransaction.function_code) and, in complete(), reject responses whose FC is neither request_FC nor request_FC|0x80 with a dedicated ClientError (e.g. UnexpectedFunctionCode { expected, got }). Add a client test that injects a txn-id-matching response with a mismatched FC and asserts the negative confirmation.

### (rtu-framing) Serial RtuCodec decoder has no MAX_RTU_ADU_SIZE upper bound
- **Evidence:** RtuCodec::decode (crates/rusty-modbus-frame/src/rtu.rs:28-56) only checks MIN_RTU_FRAME (4) then consumes the entire buffer via src.split_to(src.len()) with no 256-byte ceiling. The RTU-over-TCP codec correctly caps the scan at MAX_RTU_ADU_SIZE and returns FrameError::Truncated past it (crates/rusty-modbus-frame/src/rtu_tcp.rs:38,61-63), but the serial codec does not. Per RTU-FRAME-002 a decoder should reject frames larger than 256 bytes; with no bound, a driver that buffers a stream of bytes without silence framing could feed an oversized 'frame' that is processed (or repeatedly fail CRC over an ever-growing buffer).
- **Fix:** Mirror the rtu_tcp bound in the serial RtuCodec: if src.len() exceeds MAX_RTU_ADU_SIZE, return FrameError::Truncated (or discard) rather than splitting the whole buffer.

### (server-validation) validate.rs per-FC ordering module is dead code, never called by the server
- **Evidence:** codec/src/validate.rs has correct ordering (qty 0x03 before addr 0x02) but only callers are its own tests and spec_validation.rs. Live path handler.rs:31 uses decode_request, dispatch_request, DataStore check_range (store/memory.rs:94); never imports validate.
- **Fix:** Wire validate.rs into dispatch_request as the single validation source, or delete it and document the decode-0x03/store-0x02 split.

### (server-validation) FC2B/0E Read Device ID: no validation of code or Object Id (violates ORDER-FC-DEVID-01)
- **Evidence:** handler.rs:213-214 to build_device_id_response (handler.rs:380) reads device_id_code via unwrap_or(0x01), no validation of 01-04, ignores Object Id. Section 6.21 Fig 30: bad code -> 0x03, individual (04) unknown id -> 0x02. Typed device_id.rs:39-40 validates but is bypassed by generic mei.rs.

### (tls-security) No certificate revocation (CRL/OCSP) checking
- **Evidence:** tls_config.rs:72-87 builds WebPkiClientVerifier::builder(...).build() with no .with_crls(...); client side (tls_config.rs:46-49) uses with_root_certificates with no revocation config. Grep for crl/Crl/CRL/revocation/ocsp across crates/rusty-modbus-tls/src returns NONE. Modbus/TCP Security Spec v36 §8.2 Table 5 (VerifyServerCertSig/VerifyClientCertSig) mandates 'check the revocation status of each certificate in the chain' for both peers.
- **Fix:** Add CRL support via rustls WebPkiClientVerifier::builder(roots).with_crls(crls) on the server and a webpki verifier with CRLs on the client, sourcing CRL DER from config (e.g. an optional Vec<PathBuf>). At minimum, document the gap explicitly as a known deviation from spec §8.2 so operators don't assume revoked certs are rejected.

### (tls-security) Hand-rolled ASN.1 UTF8String parser in role.rs is fragile and can leak DER bytes into the role
- **Evidence:** role.rs:29-36 manually parses the extension value: it checks `value[0] == 0x0C` and reads a single length byte `value[1]`. This only handles short-form DER lengths (<128 bytes); a long-form length (0x81/0x82...) is not handled. Worse, the fallback at role.rs:36 `String::from_utf8(value.to_vec())` returns the RAW extension octets INCLUDING the 0x0C tag and length byte as part of the role string when the short-form branch is not taken (e.g. any value not starting with 0x0C, or length-mismatch), corrupting the role used for authorization comparisons (R-22 requires the value be decoded as a single UTF8String). x509-parser is already a dependency and exposes proper DER decoding (e.g. der_parser / FromDer for Utf8String).
- **Fix:** Replace the manual byte slicing with x509-parser's DER decoder, e.g. parse the extension content as `der_parser::asn1_rs::Utf8String::from_der(ext.value)` (or `asn1_rs::FromDer`) and reject anything that is not exactly one UTF8String. Add tests with long-form lengths and a non-UTF8String extension to confirm rejection rather than silently returning garbage.

### (tls-security) allow_unauthenticated() bypass exists and its warning only fires in debug builds
- **Evidence:** tls_config.rs:72-87: when `require_client_cert == false` the verifier is built with `.allow_unauthenticated()`, permitting clients with no certificate and violating R-06/R-10/R-44 (mutual auth MUST). The mitigating warning at tls_config.rs:78-82 is gated behind `#[cfg(debug_assertions)]`, so in release builds (the actual deployment artifact) the operator gets NO indication that mutual auth is disabled. The default is safe (config.rs:78 require_client_cert: true), but the bypass is silent in production builds.
- **Fix:** Emit the warning unconditionally via a logging facade (tracing/log) rather than only under debug_assertions, so it appears in release deployments. Consider requiring an explicit, loud opt-in (e.g. a separate constructor like build_server_config_insecure or a config field named insecure_allow_no_client_cert) so disabling mutual auth cannot happen by toggling an innocuous-looking bool. Document that allow_unauthenticated still validates a cert IF presented but accepts clients that present none.

### (pool) Failed connect after eviction destroys a healthy idle connection for nothing
- **Evidence:** pool.rs:122-124: when the pool is full, get() evicts (swap_remove) an idle non-priority entry and increments active_count while holding the lock, then releases the lock and attempts TcpTransport::connect at pool.rs:131. If connect fails, the error arm at pool.rs:143-147 only does active_count = active_count.saturating_sub(1); the already-evicted idle connection (a live, healthy TCP socket) was dropped at line 123 and is gone. So a transient connect failure to a new address silently tears down a good cached connection to a different address, increasing churn and reconnect cost precisely when the network is flaky.
- **Fix:** Defer eviction until after a successful connect: reserve the slot (increment active_count) under the lock, connect outside the lock, and only swap_remove/evict an idle entry once the new connection is established (or roll back without having destroyed anything on failure). Alternatively re-check capacity and evict lazily on insert.

### (gateway) Broadcast forwarding ignores serial_timeout, spawns unbounded fire-and-forget tasks, and drops all failures
- **Evidence:** gateway.rs:133-148: for a broadcast (unit 0) the handler iterates route_table.all_backends() and for each spawns a detached task that connects with TcpConfig::default() (gateway.rs:140) — i.e. a 5s connect_timeout and 30s read/write timeouts (config.rs:26-35), entirely ignoring the configured serial_timeout (which forward_to_backend does honor at gateway.rs:166-170). Each broadcast spawns N unbounded tokio tasks with no concurrency cap and no join; send errors are swallowed by `let _ =` (gateway.rs:142). A client sending many broadcasts can spawn unbounded background connect tasks (resource growth / DoS). Also, because broadcasts open fresh connections concurrently with normal traffic on the same backend, they violate the half-duplex serialization concern above.
- **Fix:** Reuse the per-backend serialized connection for broadcasts, apply serial_timeout to the connect/send, and bound concurrency. Per Modbus spec a broadcast must still respect bus turnaround timing on RTU; queue it through the same per-backend transaction lock instead of detached tasks.

### (performance) No benchmark exercises concurrent in-flight pipelining — the headline feature is unmeasured

## Ecosystem positioning

As of mid-2026 the Rust Modbus ecosystem is mature but fragmented, with no single crate covering the full breadth that rusty-modbus targets. The landscape: (1) tokio-modbus (slowtec) is the de-facto async standard — ~1.28M all-time / ~197K recent downloads, 539 GitHub stars, MIT/Apache-2.0, MSRV 1.76, latest 0.17.0 (Oct 2025). It does TCP + RTU + RTU-over-TCP, async + sync, client + server. Its TLS is NOT a first-class feature flag — there is no `tls`/`server-tls` feature in 0.17 (features are just rtu/tcp/*-server/*-sync); TLS is only example code where the user manually wraps the socket with tokio-rustls. It is not pipelined (requests are serialized), has no no_std, no pool, no gateway abstraction, no Python bindings. (2) rmodbus (alttch) is a sans-IO no_std codec/context framework — ~179K all-time / ~25K recent downloads, 169 stars, Apache-2.0, latest 0.12.2. It is the closest analog to rusty-modbus's no_std codec layer ONLY; it deliberately ships no transports, no client/server runtime, no TLS. (3) The bare `modbus` crate (hirschenberger/modbus-rs) is a legacy sync TCP-focused client — 461K all-time downloads (mostly historical), 108 stars, MIT, last release v1.1.3 Feb 2026 but still synchronous/blocking and TCP-only. (4) rodbus (Step Function I/O) is the only existing crate with first-class TLS + x.509 auth and C/C++/.NET/Java bindings — but it is NON-COMMERCIAL-licensed (production use requires a paid license), only ~22K downloads, 107 stars. (5) Smaller/niche: modbus-core (slowtec no_std base, 13K dl), voltage_modbus (TCP+RTU, 2.4K dl), libmodbus-rs (C FFI bindings, unmaintained since 2017), easy-modbus, modbus-rtu, modbus-mapping (register-mapping derive macros), modbus-relay (TCP→RTU relay). NAMESPACE: `rusty-modbus` and `rusty_modbus` are both FREE on crates.io; bare `modbus` is taken (legacy). rusty-modbus's genuine differentiation is the combination no other single crate offers: first-class integrated TLS (not example-only), a pipelined async client, an OSS-licensed gateway + connection pool, and Python bindings — all under a permissive license with zero unsafe. The main adoption risks are mindshare/maturity gap vs tokio-modbus and a few features OSS users will expect that should be confirmed present (Modbus ASCII, serial RTU on real hardware, sync client wrapper, register-mapping/derive ergonomics).

- **[high]** tokio-modbus is the dominant incumbent (539 stars, ~1.28M downloads) and sets the baseline rusty-modbus must beat
    - Position rusty-modbus explicitly as 'the batteries-included successor to tokio-modbus' in README/docs, with a feature-comparison table and a migration guide. Do not try to out-minimal tokio-modbus; win on the integrated stack (TLS + pipeline + pool + gateway + sim + CLI + Python) that tokio-modbus users currently have to assemble themselves. Mirror tokio-modbus's permissive MIT/Apache-2.0 dual license to remove any licensing friction for switchers.
- **[high]** First-class integrated TLS is a real differentiator: tokio-modbus has no TLS feature flag (examples only), and the only crate with true TLS+x.509 is non-commercially licensed
    - Lead marketing with 'production-ready, permissively-licensed Modbus/TCP Security (TLS) out of the box — no manual rustls wiring, no commercial license.' Explicitly contrast with tokio-modbus (example-only) and rodbus (non-commercial). Ensure the TLS implementation follows the Modbus/TCP Security spec (port 802, role-based x.509 OID) to back the claim credibly.
- **[medium]** Pipelined async client is unique among pure-Rust crates — tokio-modbus and others serialize requests
    - Publish a benchmark (you already have rusty-modbus-benchmarks/tcp_latency) showing throughput vs tokio-modbus on a multi-request workload — pipelining is only compelling if quantified. Document the per-connection in-flight limit and timeout-sweep semantics, and note correctness for RTU (where bus-level serialization is physically required — pipelining must be TCP/TLS-only or per-unit-id aware).
- **[info]** rmodbus is the only direct competitor to the no_std codec layer — and it is sans-IO only, validating rusty-modbus's layered design
    - When pitching to embedded users, benchmark the no_std codec against rmodbus/modbus-core (binary size, cycles). For app developers, the pitch is 'rmodbus's sans-IO purity at the bottom, but you don't have to write your own I/O.' Make sure the codec crate is independently publishable/usable so embedded users can adopt just Layer 0, the way they currently adopt rmodbus.
- **[medium]** OSS users will expect Modbus ASCII and serial-RTU-on-real-hardware support — confirm coverage to avoid a perceived gap
    - Confirm and document: (a) does RTU run over real serial (tokio-serial/serialport) and is it tested on hardware?; (b) is Modbus ASCII supported or explicitly out of scope? If ASCII is omitted, state so deliberately ('ASCII is legacy; not supported') rather than leaving it ambiguous. Add an RTU-on-serial example to match tokio-modbus's examples/rtu-*.
- **[medium]** A synchronous/blocking client wrapper is table-stakes for the industrial audience — verify it exists for Rust (not just Python)
    - Provide a blocking Rust client wrapper (owning its own current-thread tokio runtime, mirroring the Python SyncModbusClient) behind a `sync` feature. This directly captures the large `modbus`-crate sync user base and matches tokio-modbus's feature parity. Document it prominently — it is a low-effort, high-demand checkbox.
- **[medium]** Python bindings are a credible, near-unique differentiator — no established pure-Rust Modbus crate ships PyO3 bindings
    - Treat Python as a first-class go-to-market channel, not an afterthought: publish wheels to PyPI (manylinux/macos/windows), benchmark against pymodbus (pure-Python) to show the Rust speed advantage, and document async (asyncio) interop. This is likely the single fastest path to download volume given pymodbus's massive Python user base looking for performance.
- **[medium]** Gateway + connection pool under a permissive license is unmatched in the OSS Rust ecosystem
    - Document the gateway/pool against the Modbus Messaging Implementation Guide section it implements, with a runnable example (TCP-front, multiple RTU-back). Position as 'build a Modbus aggregator/proxy without writing your own connection management.' This is also a natural CLI showcase (a one-command gateway binary).
- **[low]** Namespace is clear: `rusty-modbus` and `rusty_modbus` are both available; bare `modbus` is taken (and undesirable to target)
    - Publish under `rusty-modbus` now to lock the name (squatting risk is low but non-zero). Reserve the 14 sub-crate names early (rusty-modbus-codec/types/frame/tcp/rtu/tls/pool/client/server/gateway/sim/conformance/benchmarks + facade) in the publish order documented in CLAUDE.md, since a single taken sub-name would force a rename. For the Python package, `rusty_modbus` on PyPI should also be checked/reserved (PyPI is a separate namespace not covered by the crates.io check).
- **[high]** Maturity/mindshare gap and proof-of-correctness are the biggest adoption blockers — 538 tests and conformance suite are the counter-narrative to lean into
    - Make correctness the headline trust signal: put the conformance/test count and 'zero unsafe' badges at the top of the README, link the conformance suite, and publish a coverage report. Compared to incumbents, 'spec-conformance-tested + zero unsafe + TLS' is the credibility wedge. Also consider a public interop test against pymodbus/tokio-modbus/libmodbus servers to demonstrate real-world compatibility, and reach 1.0 with a stability commitment sooner rather than later, since 0.x signals instability to industrial buyers.
- **[low]** Register-mapping ergonomics (derive macros / typed registers) is an expected convenience rusty-modbus does not appear to offer
    - Consider an optional derive/mapping layer (e.g. a #[derive(ModbusRegisters)] mapping struct fields to register offsets with endianness/scaling) as a separate opt-in crate. Not core to launch, but it is a frequently-requested ergonomics feature that would broaden appeal beyond protocol purists and differentiate from the low-level tokio-modbus/rmodbus APIs.
- **[info]** libmodbus C-bindings are effectively dead — reinforces the 'pure Rust, zero unsafe' positioning
    - In comparison docs, include a 'coming from libmodbus / C' section: no C toolchain, no unsafe FFI, no LGPL, cross-compiles cleanly, with feature parity (TCP/RTU/TLS, client/server). This captures the migration-from-C segment that the dead Rust bindings no longer serve.
